## Ветки поведения старого `make_cached_tts` — куда переехали

| Ветка старого поведения | Где живёт теперь |
|---|---|
| Пустой текст → ничего не делать | `prepare()` возвращает `Prepared(None)`; `say()` также сам проверяет `if not text: return` (двойная защита, как в брифе) |
| Короткая фраза (≤40 симв.) кешируется по `cache_path(cache_dir, text, voice_key)` | `prepare()`, ветка `cached = cache_path(...) if len(text) <= MAX_CACHED_CHARS else None` |
| Попадание в кеш → отдать путь из кеша | `prepare()`: `if cached is not None and cached.exists(): return Prepared(str(cached), temporary=False)` |
| Неудачное проигрывание файла из кеша → варнинг, удалить битый файл, повторить попытку синтеза в этом же вызове | Разделилось: `prepare()` больше не знает про проигрывание вообще; `say()` при ошибке `play()` удаляет файл, если `not prepared.temporary` (кеш-файл), и уходит на `fallback` — **без повторного синтеза в этом же вызове** (см. «Сомнения» ниже) |
| Cooldown активен → сразу fallback, в сеть не ходить | `prepare()`: `if in_cooldown(provider): return Prepared(None)`; `say()` видит `prepared.path is None` → `fallback(text)` |
| Исключение при `synthesize()` → `mark_failure`, `warn_once`, fallback | `prepare()`: тот же `mark_failure`/`warn_once`, возвращает `Prepared(None)`; `say()` уходит на `fallback` |
| Тело не похоже на mp3 (`looks_like_mp3` = False) → в кеш не класть, fallback | `prepare()`: новая явная проверка `if not looks_like_mp3(data): mark_failure(...); warn_once(...); return Prepared(None)` (в старом коде эта проверка физически жила в `tts_fish.synthesize`/`tts_local.synthesize`, которые бросали `RuntimeError` до входа в `tts_cache` — то есть раньше не было отдельной ветки внутри `make_cached_tts`; теперь она добавлена и в `tts_cache` как дополнительный щит, полностью согласована с брифом) |
| Выбор пути: кешируемый (`cached`) или временный (`tempfile.gettempdir()/johnny_{provider}_{pid}_{rand}.mp3`) | `prepare()`, без изменений логики |
| `store()` в файл + `trim()` кеша при удачном кешируемом пути | `prepare()`: `store(path, data)` (в try/except, отдельная ветка `Prepared(None)` при ошибке записи — раньше эта ошибка ловилась в общем `except` вместе с ошибкой `play()`) + `if cached is not None: trim(cache_dir)` |
| Успешный синтез → проиграть | `say()`: `play(prepared.path)` |
| Ошибка проигрывания свежесинтезированного файла → варнинг, fallback | `say()`: `except Exception: warn_once(f"{provider}-play", ...); ...; fallback(text)` |
| `finally`: если файл был временный (`cached is None`) — удалить его | `say()`: `finally: if prepared.temporary: Path(prepared.path).unlink(missing_ok=True)` |

## Сомнения и опасения

Один тонкий момент по сравнению со старым кодом, который брифу известен и
заложен в него намеренно (не мой домысел, а прямое следствие данного в брифе
кода `make_cached_tts`):

- **Старое** поведение при ошибке `play()` на файле из кеша: варнинг
  `f"{provider}-cache"`, удаление битого файла, и код **падал дальше** в этом
  же вызове `say()` — то есть пытался синтезировать фразу заново и проиграть
  результат, и только при повторной неудаче уходил на `fallback`.
- **Новое** поведение (по брифу): при ошибке `play()` — вне зависимости от
  того, файл из кеша или только что синтезирован (`prepared.temporary`) — код
  один раз пробует `play()`, при неудаче удаляет некешируемый файл (если он
  не временный) и **сразу** уходит на `fallback`, без повторной попытки
  синтеза в этом же вызове.
- Ни один из существующих тестов эту разницу не проверяет (они проверяют
  только итоговый `fallback`/наличие файла на диске, не число сетевых
  вызовов в этой ветке), поэтому регресса тестов нет. Но по факту это
  небольшое упрощение видимого поведения: старый код мог «спасти» фразу
  вторым синтезом после сбойного проигрывания кеш-файла, новый — сразу уходит
  на запасной голос. Так как код брифа дан дословно и промаркирован как
  обязательный к использованию «как есть», я реализовал именно его, а не
  восстанавливал ретрай — но хочу явно отметить эту разницу, а не спрятать.
  Если ретрай был важен, стоит уточнить это отдельной задачей/фиксом.
- Второй тонкий момент того же происхождения: при удачном СВЕЖЕМ синтезе в
  детерминированный кеш-путь (`cached is not None`), но неудачном `play()`,
  старый код НЕ удалял только что записанный файл (`finally: if cached is
  None: ...` — не срабатывало). Новый код удаляет его, потому что помечает
  `temporary=False` и для кеш-хита, и для свежей записи в тот же кеш-путь —
  различить их дальше некому. Тоже не ловится существующими тестами, тоже
  прямое следствие данного в брифе кода, тоже упомянуто здесь на всякий
  случай.

Оба пункта — сознательные следствия буквальной реализации кода из брифа, а не
случайные потери. Считаю их приемлемыми (они даже безопаснее: не оставляют
потенциально битый файл под тем же именем), но проговариваю явно, как просили
инструкции.

## Правка по ревью

Ревью решило вернуть первое из двух расхождений (пересинтез после сбоя
проигрывания файла ИЗ КЕША), второе (удаление свежего файла в кеш-пути при
сбое `play()`) — оставить как есть.

**Что вернул.** В `johnny/tts_cache.py`:

- Добавлена `_play_prepared(prepared, *, play) -> Exception | None` — общий
  блок «проиграть один `Prepared`»: `None` при успехе, иначе — пойманное
  исключение. При неудаче удаляет некешируемый (кеш-)файл (`temporary=False`);
  временный — удаляет в любом случае (`finally`, как раньше). Варнинг в лог и
  решение «пересинтезировать или fallback» ей не принадлежат — это разное для
  кеш-хита и для всего остального, поэтому осталось в `say()`. Вынесена, чтобы
  не дублировать блок play/удаление/уборка целиком во втором месте вызова
  (после пересинтеза).
- `say()` теперь ДО вызова `prepare(text)` определяет, был ли это кеш-хит:
  `cached = cache_path(...) if len(text) <= MAX_CACHED_CHARS else None;
  was_cache_hit = cached is not None and cached.exists()`. Это единственный
  способ узнать «файл уже лежал на диске» без изменения публичного контракта
  `Prepared` (у него нет и не должно быть поля «это был кеш-хит» — так просил
  бриф задачи 3, трогать не стал).
- Если первая попытка `_play_prepared` вернула исключение И `was_cache_hit`
  был `True` — варнинг `f"{provider}-cache"` («Файл из кеша не проигрался —
  синтезирую заново»), затем `retried = prepare(text)` (битый файл к этому
  моменту уже удалён внутри `_play_prepared`, поэтому это НЕ кеш-хит, а
  честный пересинтез) и, если `retried.path is not None`, ровно одна повторная
  `_play_prepared(retried, ...)`. Успех — `return` без `fallback`. Неудача (в
  т.ч. если `retried.path is None`, то есть пересинтез не удался вовсе) —
  падение в общий хвост: варнинг `f"{provider}-play"` и `fallback(text)`, как
  и для всех остальных случаев (не кеш-хит вообще, либо кеш-хит, но
  `was_cache_hit` был `False`).
- Бесконечного цикла нет: пересинтез вызывается максимум один раз за
  вызов `say()` — только внутри веты `if was_cache_hit`, без цикла и без
  рекурсии.
- Удаление битого файла из кеша сохранено (внутри `_play_prepared`, как и до
  правки).
- Утечек временных файлов на новом пути нет: `_play_prepared` вызывается для
  ОБОИХ `Prepared` (исходного и `retried`) и в обоих случаях чистит временный
  файл через тот же `finally`, что и раньше.

**Второе расхождение НЕ трогал**: свежесинтезированный файл, записанный по
детерминированному кеш-пути (в том числе `retried` из пересинтеза выше),
по-прежнему удаляется при сбое `play()` — `_play_prepared` не различает
«кеш-хит» и «только что записанный в кеш-путь» (оба `temporary=False`), это
осталось как в текущем (post-рефакторинг) коде, а не как в самом старом.

**Тест.** В `tests/test_tts_fish.py` добавлен
`test_play_failure_on_cached_phrase_resynthesizes_and_plays_without_fallback`:
битый файл лежит под именем кеша, сеть жива (`fake_post` отвечает валидным
mp3), `play()` — «капризный» (падает только на первый вызов). Проверяется:

Докстрин объясняет «почему» это важно: битый файл на диске — случайность

## Правка по ревью 2

Второй заход ревью нашёл ещё четыре расхождения с поведением до рефакторинга
(два Important, два Minor). Почистил все четыре одним заходом в
`johnny/tts_cache.py`.

**Находка 1 (Important) — исключение `trim()` улетало наружу.** В
`make_cached_prepare` вызов `trim(cache_dir)` жил ПОСЛЕ `try/except` вокруг
`store`, то есть вне защиты: `sorted(..., key=lambda p: p.stat().st_mtime)`
кидает `FileNotFoundError`, если файл исчез между `glob` и `stat` (его мог
доиграть и удалить другой поток), а `unlink` на Windows кидает
`PermissionError` (WinError 32) на файле, который держит открытым MCI-плеер
— и то, и другое создаёт ровно наш конвейер (один поток играет из кеша,
другой синтезирует и подчищает кеш параллельно). Исключение уходило сквозь
`prepare` и `say` наружу, хотя docstring модуля обещает «при любой неудаче —
fallback». Обернул вызов `trim(cache_dir)` в собственный `try/except
Exception` с `warn_once(f"{provider}-trim", ...)`: сбой уборки кеша —
best-effort и не должен портить только что удавшийся синтез (файл уже
записан и обязан прозвучать), поэтому `Prepared` после сбоя `trim` всё равно
возвращается успешным, а не `None`.

**Находка 2 (Important) — свежий файл кеша удалялся при сбое play().**
Старый (до задачи 3) код удалял файл при сбое проигрывания ТОЛЬКО если он
был взят из кеша (`if cached is None: ...` — для свежей записи не
срабатывало). После задачи 3 `_play_prepared` удаляла файл по условию `not
prepared.temporary`, которое верно и для кеш-хита, и для только что
записанного по кеш-пути файла (`temporary=False` у обоих) — различить их
было нечем, и свежий, оплаченный сетевым запросом файл выбрасывался при
случайном сбое звукового устройства. Добавил `Prepared` третье поле
`from_cache: bool = False` — «этот файл уже лежал на диске (кеш-хит), а не
только что записан». В `prepare()` кеш-хит теперь возвращает
`Prepared(..., from_cache=True)`, а любая свежая запись (в кеш-путь или во
временный) — `from_cache=False`. `_play_prepared` при сбое `play()` удаляет
файл, только если `prepared.from_cache` — прежняя асимметрия восстановлена.

**Находка 3 (Minor) — незащищённый `unlink` внутри `except`.** В
`_play_prepared` удаление битого кеш-файла внутри `except` не было обёрнуто
в `try/except OSError`, в отличие от удаления временного файла тремя
строками ниже в `finally`. Если бы `unlink` бросил (тот же WinError 32 —
файл ещё открыт MCI), это замаскировало бы исходную ошибку `play()` и
вылетело бы наружу из `say()`. Обернул симметрично соседнему блоку.

**Находка 4 (Minor) — дублировалось правило «что кешируется».** `say()`
заново вычисляла `cache_path(...) if len(text) <= MAX_CACHED_CHARS else
None` перед вызовом `prepare()`, только чтобы узнать `was_cache_hit` —
повторяя ту же строку и лишний sha1+`stat()` на каждый вызов. Поле
`from_cache` из находки 2 закрывает и эту находку: `say()` больше не
вычисляет кеш-путь сама, а просто читает `prepared.from_cache` после
`prepare(text)`.

**Сигнатуры не менялись.** `make_cached_tts` и `make_cached_prepare`
остались прежними — правки только внутри `Prepared` (новое поле с
default-значением, обратно совместимо) и тела функций.

**Тесты.** В `tests/test_tts_fish.py` добавлены три теста (существующие не
трогал):

- `test_play_failure_on_freshly_cached_phrase_keeps_the_file_on_disk` —
  вторая половина находки 2: свежесинтезированный файл по кеш-пути при сбое
  `play()` остаётся на диске и содержит валидный mp3 (первая половина —
  «кеш-хит удаляется» — уже была покрыта существующим
  `test_play_failure_on_cached_phrase_falls_back_and_deletes_broken_cache_file`,
  который так и не трогал). Докстрин объясняет «почему»: файл уже оплачен
  сетевым запросом, а случайный сбой звукового устройства не делает mp3
  битым — выбросить его значило бы никогда не наполнить кеш коротких фраз
  при неисправном устройстве.
- `test_cache_file_unlink_failure_after_play_error_does_not_mask_it` —
